# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"דוכן הספרים" (the book stand) — a point-of-sale app for a book fair / seller stand: browse a catalog, build a cart, apply discount rules, record sales, and export reports. Hebrew UI, RTL layout (`index.html` sets `lang="he" dir="rtl"`). No backend — all data lives in the browser's `localStorage`.

## Commands

All standard commands are in `package.json`'s `scripts`. Two things not obvious from the names alone: there's no separate typecheck script — use `npx tsc -b --noEmit` directly; and `build:offline`/`build:offline:demo` produce single-file `dist*/index.html` builds meant for handing to non-technical testers via `file://`, the "demo" variant pre-seeded with a mock catalog (see "Demo seeding" below).

**Known gap**: a user reported a blank white screen opening one of these builds via `file://` on their phone. The likely cause — `<script type="module">` (which Vite's HTML pipeline emits regardless of `build.rollupOptions.output.format`; `vite-plugin-singlefile` just inlines whatever Vite decided to emit) is documented to sometimes fail to execute at all under `file://`'s opaque origin on some mobile browsers — is still unfixed and unconfirmed either way. An attempted fix (forcing `iife` output + relocating the inlined script to the end of `<body>`, since `defer`/`async` are spec-ignored on a `src`-less inline script) was tried and reverted: it broke the build outright via a file-duplication bug in the Vite/Rollup `closeBundle` write-timing that resisted diagnosis even with direct instrumentation. A real fix needs either `@vitejs/plugin-legacy` (new dependency, Babel-based nomodule fallback — verify it still cooperates with `vite-plugin-singlefile`'s inlining) or a properly-tested from-scratch reimplementation of the relocate-to-end-of-body approach — **still needed for the `file://`/offline-build distribution path specifically**, which this doesn't change. **Confirmed resolved for real device access via Firebase Hosting** (Phase 2 Task 20, 2026-09-23): opening the app at its live `https://` Hosting URL on the same phone that previously showed the blank screen no longer reproduces it — consistent with the bug being specific to `file://`'s opaque origin (Hosting is neither `file://` nor opaque). This confirms the corresponding half of Task 20's own verify criteria; the `file://` root cause itself is still unpatched for anyone still relying on the offline single-file build. What *is* fixed: an uncaught Firebase/Firestore init failure (e.g. IndexedDB unavailable on the same opaque `file://` origin) no longer blanks the whole app — see `src/sync/firebaseConfig.ts` and `src/components/ErrorBoundary.tsx` below. **Testing workaround in the meantime**: serve `dist-offline/` over plain HTTP on the LAN (e.g. `python3 -m http.server <port> --bind 0.0.0.0` from the build's output directory) and open `http://<mac-lan-ip>:<port>/` from the phone's browser — confirmed working on both Android and iPhone Safari, and sidesteps `file://`/Quick-Look ambiguity entirely (iOS Mail/WhatsApp's built-in file previewer often doesn't run JavaScript at all, which can look identical to a real bug). **Caveat**: plain `http://` to a non-localhost address is an insecure context, so `crypto.randomUUID()` is unavailable there — `src/domain/ids.ts`'s `newId()` already falls back to `crypto.getRandomValues()` for this (see below), but keep this in mind if some *other* browser API starts silently failing only when testing this way and not via `file://`/`https://`.

## Deploy (Phase 2 Task 20, in progress)

Two fully separate Firebase projects — prod (`stall-8e1fc`) and dev (`stall-8e1fc-dev`) — each with its own Hosting site, Firestore, and shared stall Auth account, so dev testing never touches real sale data.

- `.env.local` holds prod's `VITE_FIREBASE_*`/`VITE_STALL_EMAIL` values (unchanged, same as before this task).
- `.env.development.local` (gitignored, same pattern) holds dev's values. Vite layers it on top of `.env.local` whenever `--mode development` is used.
- `npm run build:dev` (`tsc -b && vite build --mode development`) produces a dev-configured build; the plain `npm run build` stays the prod build. Verified: `stall-8e1fc-dev` only appears in the `build:dev` output, `stall-8e1fc` only in the plain `build` output.

**Actual Hosting deploy tooling is deliberately not wired up.** Firebase Hosting has no manual/browser-upload path — the only way to push files there is the Firebase CLI (`firebase deploy`) or an equivalent API call, and the user opted out of using the CLI at all for this task. `firebase.json`/`.firebaserc`/`firebase-tools` were added, tried, and then removed for this reason — check `git log --oneline -- firebase.json .firebaserc` on `phase2`/`dev` if that history is ever useful again. How this app's `dist/` build actually reaches Firebase Hosting (CLI run by the user directly, a future CI step, or a different hosting target entirely) is still an open question.

**Branch mapping** (settled regardless of the above): `main` → prod, `dev` (branched off `phase2`) → dev. Feature branches (`phase2`, and future ones) merge into `dev`; `dev` merges into `main` when a batch of work is ready for prod. `main` has not been touched by this task.

## Claude Code tooling for this repo

`.claude/` (shared between the main checkout and every worktree) has project-committed skills, a subagent, and a hook — reach for these instead of redoing the underlying work by hand:

- **`verify` subagent** (`.claude/agents/verify.md`) — runs the full pre-commit chain (`npx tsc -b --noEmit` → `npm run test -- --run` → `npm run lint` → `npm run build`) and reports a terse pass/fail, without dumping four commands' worth of output into the main conversation. Dispatch it after a code change, before committing.
- **`serve-offline-build` skill** — builds `dist-offline/` (sync-configured, Firebase-env-vars-blanked "phase 1", or the demo variant) and serves it over the LAN via `python3 -m http.server --bind 0.0.0.0`, since opening these builds via `file://` directly is unreliable on mobile (see the "Known gap" note above). Explicit-invocation only (`disable-model-invocation: true`) — it binds a server to the network, so it shouldn't fire on its own.
- **`browser-repro` skill** — a bundled, parametrized Playwright driver (`scripts/repro.mjs`) for reproducing browser/mobile-compat bugs: console/pageerror capture, screenshots, and this app's known simulation tricks (forced-crash query param, `window.indexedDB.open` failure, deleting `crypto.randomUUID`/`navigator.clipboard` to simulate an insecure context). `references/secure-context-apis.md` tracks which browser APIs this app has hit restrictions on and where they're already handled.
- **`field-bug-triage` skill** — for a bug reported from a real device rather than reproduced locally: ask for the user's copied `DebugLogPanel` export (see "Debug log" below) before guessing, and — informed by this app's own history (a `crypto.randomUUID` fix that initially missed a second call site) — don't stop investigating at the first matching call site.
- **Pre-commit nudge hook** (`.claude/settings.json` + `.claude/hooks/pre-commit-check.sh`) — fires before any `git commit`, informational only (always `permissionDecision: "allow"`, never blocks): notes if `src/`/config is staged without `CLAUDE.md`/`roadmap.md` staged alongside, and if the `verify` subagent hasn't run since the last source edit.

## Architecture

### Data flow: store → context → pages

- `src/data/localStorageDriver.ts` — thin `readJSON`/`writeJSON` wrapper over `localStorage`, all keys prefixed `shaatnez:v1:`.
- `src/data/store.ts` — one get/save function pair per entity (categories, items, discount rules, labels, sale records, payment methods, creators, event name). This is also where **backward-compatible normalization** happens: whenever a field is added to a persisted type, `store.ts` defaults it here on read (e.g. `item.labelIds ?? []`, `rule.stackable ?? true`) so old localStorage data doesn't break. When adding a new field to a persisted type, add its default here. Event name is the one exception to "one value per entity": it's stored as a timestamped `EventNameRecord` (`{ name, updatedAt }`, migrated transparently from the pre-Phase-2 bare string) so it can take part in sync's LWW conflict resolution like every other config entity.
- `src/context/AppDataContext.tsx` — the single global state container. Loads everything from `store.ts` into React state on mount, exposes CRUD/reorder functions for every entity, and persists back to `store.ts` on every mutation (`persistXxx` helpers do `setState` + `store.saveXxx` together). All pages read/write through `useAppData()`; there is no other state management.
- Pages (`src/pages/...`) are thin: they call `useAppData()` and compose components. `src/App.tsx` owns the single `useCartState()` instance above the tab switch so an in-progress sale survives navigating between tabs.

### Pricing engine (`src/domain/pricing.ts`)

`evaluateSale(cart, categories, items, labels, creators, rules, manualDiscount?)` is the one function that turns cart lines into priced totals. Internally it expands cart lines into per-unit `Unit` records (one per physical item, not per line) so discounts can apply below the line level, then:

1. Filters rules to `enabled` ones whose optional `trigger` condition (min qty of some selector present in the cart) is met.
2. Splits into **exclusive** (`stackable: false`) and **stackable** (`stackable: true`, the default) rules.
3. Exclusive rules only ever claim units with `discountAgorot === 0 && !locked`. When several exclusive rules could claim the same units, it greedily awards each round to whichever remaining rule currently gives the customer the biggest discount, then locks those units so nothing else can touch them — this is what "the discount can't combine with others" means in the UI.
4. Stackable rules then apply in the seller's configured order (`DiscountRuleManager`'s up/down reordering), skipping any locked units, and can layer on top of each other and of already-discounted units.
5. `manualDiscount` (a cashier-entered flat/percent adjustment from the sale page) is applied last, on the post-rule total, and isn't attributed to any line or creator share.

Rule kinds (`src/types/discount.ts`): `stepDiscount` (discount from the Nth matching unit onward), `bundlePrice` (fixed price per group of N units), `comboBundle` (fixed price for a set of different components together). Each rule kind has a pure `computeXAssignments(rule, pool) -> Assignment[]` function (never mutates) used both to trial exclusive-rule candidates and to actually apply a rule — mutation only happens where the result is committed in `evaluateSale`. Money is handled in agorot (integer cents) internally via `toAgorot`/`fromAgorot` to avoid floating-point drift; shekels only appear at the boundaries.

`ItemSelector` (`src/types/selector.ts`) — `{ type: 'filter', categoryIds, labelIds, creatorIds }` (OR-matched within each list, AND across lists) or `{ type: 'item', itemIds }` — is the shared targeting mechanism used by discount rule targets, triggers, and combo components.

### Cart state (`src/hooks/useCartState.ts`)

Wraps lines + manual discount + comment, and memoizes `evaluateSale(...)` as `evaluated`. Used both by `SalePage` (fresh cart, persists across tab switches) and `RecordsPage/RecordEditor` (seeded from an existing `SaleRecord` to edit a past sale in place, reusing the exact same cart UI).

### Shift seller (`src/domain/shiftSeller.ts`, `src/hooks/useShiftSeller.ts`, `src/pages/ConfigPage/ShiftSellerSettings.tsx`, Phase 2 Task 17)

`ShiftSeller` (`{ name, setAt }`) is a private, device-local "who's on shift here" setting — **plain free text**, not a `Creator` reference: whoever's minding the till for a shift isn't necessarily in the `creators` revenue-share roster (an earlier version tied it to `creatorId` via a dropdown; changed after user feedback). Persisted via `store.ts`'s `getShiftSeller`/`saveShiftSeller` (same private bucket as `deviceId`/`syncOutbox` — never wired into `AppDataContext`'s `persistX`/outbox path, so it never syncs; `getShiftSeller` also degrades a value stored under the old `{ creatorId, setAt }` shape to unset rather than surfacing a name-less object, since this was never migrated). `useShiftSeller()` is a thin hook wrapper around that storage. The set/clear control (`ShiftSellerSettings`, a plain text input) lives on the **Settings page**'s "כללי" section (see below) rather than on the Sale page itself — picking it once per shift before selling starts avoids fighting with an in-progress sale's own fields, and it also sidesteps a real bug hit during manual testing: `SalePage`'s `receiver` field only reads the shift seller at mount (a `useState` lazy initializer), so a control living on the Sale page wouldn't reactively re-default an already-open sale anyway. `domain/shiftSeller.ts`'s pure `defaultReceiverForShiftSeller(shiftSeller)` resolves the shift seller's current name (`''` if unset) to seed `SalePage`'s `receiver` field at mount and again after each save — `receiver` itself stays fully required and editable per sale, this only changes its starting value. Deliberately never used on `RecordEditor` (editing a past sale shouldn't re-default to whoever's on shift *now*).

**Receiver picker (`PaymentSelector.tsx`)**: `receiver` is a `<select>` over the `creators` list plus an "אחר..." option that reveals a free-text input for anyone not yet a creator (including, commonly, the shift seller default above — which, being free text itself, often won't match a creator). Storage is unchanged: `SaleRecord.receiver` is still a plain string (either the chosen creator's name or typed text), so no migration and no changes needed to CSV/reports/record display. `isCustomReceiver` (owned by `SalePage`/`RecordEditor`, passed down as a prop, computed by checking whether the current/default receiver string matches a live creator's name) tracks which mode is showing, since deriving it purely from `receiver`'s current value can't distinguish "just chose אחר, box is empty" from "no receiver chosen yet."

### Config page layout (`src/pages/ConfigPage/ConfigPage.tsx`)

Sub-tabbed, all sections at the same level: `כללי` (`EventSettings`/`ShiftSellerSettings`/`SyncStatusPanel`/`DebugLogPanel` together), `פריטים`, `מבצעים`, `קטגוריות`, `תוויות`, `אמצעי תשלום`, `יוצרים` — `כללי` is first in the list and the default-selected tab. (Previously the `כללי`-type panels were always visible above the tab strip; moved into their own tab after user feedback so all settings live at one consistent level.)

### Reports/payouts (`src/domain/payouts.ts`, `src/domain/reports.ts`)

`computeCreatorPayouts` splits each line's *post-rule-discount* amount across its snapshotted `creatorShares` (percentages captured on the item at time of sale, not looked up live) — manual discount is deliberately excluded from this split. `SaleRecord.paymentMethodName` is likewise snapshotted at sale time (Task 16) alongside the live-reference `paymentMethodId`, so a payment method deleted later (possibly on another device, post-sync) can't corrupt historical reports; the report builders and Records-page views prefer the snapshot and fall back to a live `paymentMethods` lookup only for records saved before this field existed. `reports.ts` builds CSV row arrays (`domain/csv.ts` handles escaping/BOM-for-Excel) for the three exports on the Records page: per-sale rows, per-payment-method/receiver totals, and per-item totals.

### Adding a new persisted field

1. Add it to the type in `src/types/*.ts`.
2. Default it in the corresponding `getXxx()` in `src/data/store.ts` if old data might lack it.
3. Thread it through `AppDataContext.tsx` CRUD functions if it's user-editable.
4. If it's a new *entity* (not a field on an existing one), it needs its own outbox wiring in its `persistX` helper (`enqueue(...)`) and its own inbound handler in the `startSyncPull(...)` call — see "Sync foundations" below. Individual fields never need per-field sync config; resolution is whole-row by default.

### Tombstones and soft deletes (Phase 2)

Every shared entity (`Category`, `CatalogItem`, `DiscountRule`, `Label`, `Creator`, `PaymentMethod`, `SaleRecord`) has an optional `deletedAt?: string`. **Deleting one of these through `AppDataContext` never removes the row from state/localStorage** — it sets `deletedAt` and leaves the row in place (a "tombstone"), so a delete that's already synced elsewhere can't leave another device's concurrent edit pointing at a vanished id. `useAppData()` exposes only `isLive`-filtered rows (`src/domain/cascade.ts`), so tombstoned rows disappear from the UI exactly as a hard delete used to — but they still round-trip through the outbox as an `upsert` (Firestore's copy of the doc also just gains `deletedAt`, it's never `deleteDoc`'d). `cascade.ts` also holds the pure cascade/unlink helpers: `applyCategoryTombstone` (cascades to the category's items), `applyLabelTombstone`/`applyCreatorTombstone` (unlink from `item.labelIds`/`item.creatorShares` rather than cascading) — used directly by local deletes in `AppDataContext.tsx`. Batch variants (`applyCategoryTombstones`/`applyLabelTombstones`/`applyCreatorTombstones`, each taking the whole pulled row list instead of one id) re-run the same cascade against every currently-tombstoned row on every sync pull (Task 16) — needed because a sync-delivered tombstone lands as a plain field change via LWW merge with nothing else re-triggering the cascade, and because a concurrent item edit on another device can race a cascade's own item tombstone/unlink and win LWW, silently reverting the item to reference a category/label/creator that's already gone. Each single-row function is idempotent, so replaying already-applied tombstones on every pull is harmless and self-heals that race.

### Sync foundations (`src/sync/`, Phase 2 — in progress, Tasks 10-15 done)

Cloud sync (see the plan doc above for full design) is being built additively — the app must keep working fully offline/local-only at every point in between tasks.

- `src/sync/firebaseConfig.ts` — lazy Firestore/Auth init, gated by `isSyncConfigured` (true only when `VITE_FIREBASE_*`/`VITE_STALL_EMAIL` env vars are set). Everything below no-ops without it. **Note for tests**: Vitest loads `.env.local` like Vite does, so `isSyncConfigured` is `true` in the test process whenever a real `.env.local` is present — any test that reaches real sync code (`drain.ts`, `backend.ts`, `pinGate.ts`) must mock its dependencies rather than relying on sync being "off" by default. `initializeFirestore(...)`'s `persistentLocalCache` call is wrapped in a try/catch: it needs IndexedDB, which throws synchronously on an opaque `file://` origin on some mobile browsers (the offline single-file builds opened directly from disk) — on failure it falls back to a plain non-persistent Firestore instance instead of crashing (sync still works over the network, just without offline queueing/multi-tab coordination). Covered by `firebaseConfig.test.ts`.
- `src/components/ErrorBoundary.tsx` — the app's only React Error Boundary, mounted twice in `main.tsx` (once wrapping `PinGate`, once wrapping `AppDataProvider`/`App` inside it) as a last-resort net for whatever the Firestore fallback above and everything else doesn't catch — with none anywhere before this, any uncaught render/effect error (Firebase init included) unmounted the whole tree with zero visible feedback. Shows a Hebrew "משהו השתבש" card with a reload button; logs via `console.error` (no error-reporting service exists in this app).
- `src/sync/deviceId.ts` — stable per-device id, generated once, never synced.
- `src/sync/pinGate.ts` + `src/components/PinGate.tsx` (wraps `main.tsx`) — the stopgap access gate: the "PIN" is the password of one shared Firebase Auth email/password account, not a real per-person login (that's Phase 3). Also starts the sync drain loop (see below) once `watchStallAccess` reports signed-in.
- `src/sync/backend.ts` — thin Firestore adapter (`pushAll`/`pullAll` per entity), kept small on purpose so a future backend migration doesn't mean rewriting every call site. Only used by `SyncDebugPanel`'s one-off bulk push/pull — per-op sync goes through `outbox.ts`/`drain.ts` instead.
- `src/sync/outbox.ts` — `diffToOps` (pure prev/next diff) and `enqueue` (the persistX-facing wrapper), appending to a private `syncOutbox` localStorage key and then firing an immediate best-effort `drainOutbox()` call so an edit reaches Firestore right away. Wired into every `persistX` helper in `AppDataContext.tsx` as of Task 12.
- `src/sync/drain.ts` (Task 13) — `drainOutbox()` pushes each queued op to Firestore via `setDoc`/`deleteDoc` (per-doc, not the bulk `backend.ts` path), removing it from the outbox on success and requeuing it with `attempts`/`lastError` on failure — including a per-op timeout so one op stuck with no network can't block the queue forever (Firestore's own SDK is relied on for retrying ordinary transient failures, per the Phase 2 plan). `startSyncDrain()` wires this to fire on load/sign-in, on the browser `online` event, and on a 30s foreground interval as a catch-all — no service worker, no background sync.
- `src/sync/merge.ts` (Task 10, wired in Task 14) — `resolveLastWriteWins` (whole-row LWW by `updatedAt`) and `mergeRows` (LWW per shared id + adopt remote-only rows + keep not-yet-pushed local-only rows). Reused as-is for every one of the 7 row entities *and* for sale records specifically — "append + id-based dedup" for new sale records turned out to be exactly what `mergeRows` already does, so there's no separate merge path for them. Also `findLocalWins(remote, merged)` — **load-bearing for actual convergence, not just a nicety**: Firestore's stored doc is whatever `setDoc()` last overwrote it with (network arrival order), not whatever `updatedAt` says is newest, so if a pull-merge picks the local row over a stale remote one, that row has to be pushed back or the stale doc — and any other device reading it — never gets corrected. Relies on `mergeRows` returning the winning object by reference (tested).
- `src/sync/pull.ts` (Task 14) — `startSyncPull(handlers)`: one Firestore `onSnapshot` listener per collection plus one for the `eventName` singleton doc, calling the matching handler with the raw snapshot rows whenever another device's push lands. Purely inbound — never touches the outbox itself, so it can't loop a pulled change back into a push on its own (see `findLocalWins` above for the one case that deliberately does push back).
- `src/context/AppDataContext.tsx`'s mount-time `useEffect` wires `startSyncPull` in: each handler merges the incoming rows via `sync/merge.ts`, writes to `store.ts` + state, and `enqueue()`s any `findLocalWins` corrections. Uses the **functional** `setState(current => ...)` form deliberately — an earlier version read "current" from a ref mirrored by a separate effect (to keep the `enqueue()` side effect out of a setState updater, since StrictMode double-invokes updaters in dev). That was a real production bug: Firestore's `onSnapshot` can fire within milliseconds of a local write, often before the ref-mirroring effect's next run, so the ref was frequently stale — the resulting merge would silently overwrite a just-made local edit (e.g. a newly-added creator would vanish again right after being added). The functional form is always fresh; the StrictMode double-invoke tradeoff only affects `npm run dev` and even there just re-pushes an already-correct row (harmless).
- Rule-target resolution against a tombstoned/vanished id needed no special-casing: `pricing.ts`'s selector matching is purely id-based, so once the referencing row is filtered out of what `AppDataContext` exposes, a discount rule targeting it just naturally matches nothing (locked in by Task 10's `pricing.test.ts` suite).
- `src/sync/syncStatus.ts` (Task 15) — a small external store (`useSyncExternalStore`, no polling) tracking `{online, draining, pendingCount, stuckOps, lastSyncedAt}`. `outbox.ts`/`drain.ts` call its `notifySyncOutboxChanged`/`recordSyncSuccess`/`setDraining` after they touch the outbox or Firestore, so the two UI consumers stay live: `src/components/SyncStatusBadge.tsx` (minimal always-visible dot+label, in `SideNav.tsx`'s mobile top bar and desktop sidebar) and `src/pages/ConfigPage/SyncStatusPanel.tsx` (full detail — connection status, pending count, last-synced-at, manual "sync now", stuck-op errors). Both render `null` when `!isSyncConfigured`. This replaced Task 11's temporary `SyncDebugPanel.tsx` (deleted).

### Debug log (`src/debug/errorLog.ts`, `src/pages/ConfigPage/DebugLogPanel.tsx`)

Private, device-local, never synced (same bucket as `deviceId`). `installGlobalErrorLogging()` (called once in `main.tsx`) wraps `console.error`/`console.warn` and adds `window.onerror`/`unhandledrejection` listeners, capturing everything into a capped (200-entry) ring buffer persisted to `localStorage`. Wrapping the console means every existing call site (drain.ts's failure logging, firebaseConfig's fallback notice, `ErrorBoundary.componentDidCatch`) is captured for free with no extra instrumentation. Exists because an event-handler exception shows literally nothing on screen — no error boundary, no console access on a seller's phone — so there was no way to diagnose a real bug (`crypto.randomUUID` unavailable over insecure `http://`) beyond the user manually reading and retyping a stack trace. `DebugLogPanel` (Settings page) shows the count and lets it be copied (`navigator.clipboard`, itself secure-context-only) or, when that's unavailable, manually selected from a fallback `<textarea>`.

### Demo seeding (`src/dev/demoData.ts`, `src/main.tsx`)

`seedDemoDataIfEmpty()` writes a small mock catalog through the normal `store.ts` save functions, but only if the store is empty — guarded so it can never clobber real data and is a no-op on reload. Gated behind `import.meta.env.VITE_SEED_DEMO === 'true'` (build-time only, set via the `build:offline:demo` script), so it's fully dead-code-eliminated from the normal build.
